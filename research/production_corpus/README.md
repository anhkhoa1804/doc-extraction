# enterprise-production-en-vi

The primary EN/VI production benchmark: 58 synthetic enterprise documents,
125 pages, five input formats.

## Why this exists alongside `research/hardcases/`

They answer different questions and neither replaces the other.

| | `hardcases` | `production_corpus` |
|---|---|---|
| Shape | one mechanism per document | realistic mixture |
| Size | 14 documents, all hard | 58 documents, mostly ordinary |
| Formats | PDF only | PDF, DOCX, XLSX, PPTX, PNG |
| Combinations | none | 10 documents stack 2–4 difficulties |
| Answers | *did this mechanism regress?* | *what should we build next?* |

The mechanism corpus is a regression lock and is excellent at that. It cannot
rank work, because every document in it is hard by construction — frequency
and co-occurrence are exactly the information it throws away. Ranking failure
classes by evidence rather than intuition needs a corpus where easy documents
are represented in proportion and where difficulties land together, because
that is what an enterprise document actually looks like.

## Composition

```
by format   pdf 49, docx 3, xlsx 2, pptx 2, png 2
by class    29 ordinary, 18 single-mechanism hard, 10 combination, 1 long
languages   en, vi  (Vietnamese diacritics throughout)
```

Document types: contract, invoice, financial_report, company_profile,
business_license, certificate, form, policy, technical_report,
purchase_order, scanned_admin.

Combination documents (mission §30) are the point of the corpus. Real
documents do not present one difficulty at a time:

| Document | Stacked difficulties |
|---|---|
| `cmb_scan_stamp_table_vi` | no text layer + seal + table structure |
| `cmb_scan_tiny_vi` | no text layer + 4.5 pt body |
| `cmb_stamp_table_vi` | seal + merged cells |
| `cmb_lowcontrast_stamp_vi` | faint text + occlusion |
| `cmb_multicol_table_en` | two columns + table + reading order |
| `cmb_stamp_boundary_vi` | seal crossing a cell boundary |

`long_policy_vi_60p` is 60 pages, for the memory, model-reuse and
partial-failure questions in §29.

## Safety

Every document is generated by `generate.py`. Company names, people, tax
codes and amounts are invented, and the identifiers are deliberately not
well-formed registrations. No enterprise document — public or private — is
copied or included. This matters because the corpus is committed to git and
the private corpus it stands in for is not.

**This is synthetic evidence.** It is designed to be representative, and it
is not a substitute for the real corpus. Results measured here should be
reported as synthetic, exactly as `experiments/008` and `009` do.

## Ground truth

Each document declares `must_contain` — short distinctive fragments that must
survive extraction — and, where confident garbage is the risk,
`must_not_contain`. Recall is over `must_contain`, NFC-normalized, identical
to `research/hardcases/run_benchmark.py`.

Fragments are short on purpose. Asserting whole sentences makes a benchmark
fail for reasons unrelated to extraction quality — one wrapped line or one
clipped character sinks the string. `generate.py` truncates at a word
boundary, and a validation pass confirms every born-digital document's ground
truth is actually present in its own text layer. Two generator bugs were
found that way (a rotated line running off the top of the page, and a column
of text clipped at the right edge) — both would have looked like extraction
failures rather than corpus defects.

## Regenerating

```bash
python research/production_corpus/generate.py      # writes corpus/ + manifest.json
python research/production_corpus/run_benchmark.py --strategy adaptive
```

Generation is seeded (`SEED = 20260902`). **57 of 58 documents regenerate
byte-identically**, verified by regenerating twice and comparing the manifest's
per-file `sha256`.

That did not come for free, and the first attempt was wrong: 56 of 58 files
differed between two runs of the same generator. Three separate sources of
nondeterminism had to be closed, and each would have silently made the hashes
record *which run happened* rather than *which corpus*:

| Source | Fix |
|---|---|
| PyMuPDF stamps a fresh `/ID` and `CreationDate` on every save | pinned metadata, `no_new_id=True` |
| OOXML zip entries carry their own write time | archive rewritten with a constant timestamp and sorted entry order |
| openpyxl rewrites `dcterms:modified` at save, overriding the properties object | timestamp normalized in the serialized `docProps/core.xml` |

The one exception is **`hc_encoding_vi`**, which is built by
`tests/fixtures.make_pdf_with_broken_cmap`. That helper is a shared regression
fixture and stamps its own dates; it is deliberately not modified here, so this
single document's hash changes between runs. Its *content* is stable — only the
metadata moves.

Only `manifest.json` and the generator are committed; the generated documents
and run outputs are ignored, the same policy `research/hardcases/` uses for
its working directories. The manifest carries a hash per document so a
regenerated corpus can be checked against the one a result was measured on.

## Reading the results

`run_benchmark.py` writes a failure table, not just an aggregate. Every
document that came out wrong contributes rows of
`(document, failure_type, severity, strategy, recovered, runtime)`, so failure
classes can be ranked by frequency and consequence.

Severity is about consequence rather than diff size:

| Severity | Meaning |
|---|---|
| `critical` | recall 0.0, **or** a hallucination — output that looks like success |
| `high` | recall below 0.5, or a table that was expected and not found |
| `medium` | partial loss, recall below 1.0 |

A hallucination is critical regardless of recall. Nothing downstream can
distinguish confident garbage from a successful extraction, which is the
failure mode the whole routing architecture exists to prevent.

Each run records its GPU classification (median-sampled) and CPU load. On this
shared VM a timing taken beside another project's job is an upper bound, not a
benchmark; recall is unaffected, because CPU and GPU outputs were shown
identical to 0.000 px in `experiments/006`.
